# txt2img

A Z-Image-Turbo text-to-image server, packaged as a single Docker image that
can be reached four ways from the same underlying code (`src/lib/engine.py`):

- **CLI** — pass a prompt and generation params.
- **HTTP** — submit a prompt, get a job id back, poll it, then download the result.
- **MCP tool over stdio** — pass a prompt, get a base64-encoded result back synchronously.
- **MCP tool over Streamable HTTP** — the same tool, reachable at `/mcp` on
  the HTTP server, for remote MCP clients that don't spawn a subprocess.

Only one generation ever runs at a time (one GPU, one job). HTTP jobs are
queued and processed strictly in order; the MCP tool, being synchronous,
refuses instead of queueing if a job is already in flight and points the
caller at the HTTP endpoint (see "Job queue" below) -- same design as the
`upscaler` pipeline.

## Model

- `Tongyi-MAI/Z-Image-Turbo` (Apache-2.0) — scheduler, tokenizer, VAE. Its
  own transformer weights are never loaded; the notebook/pipeline this is
  based on passes an explicit `transformer=` override.
- `jayn7/Z-Image-Turbo-GGUF`, `z_image_turbo-Q4_K_M.gguf` (Apache-2.0,
  "follows the same license as Z-Image Turbo") — the actual transformer,
  loaded via `from_single_file`.
- Text encoder: `Qwen3Model` from the Tongyi-MAI repo's `text_encoder/`
  subfolder, loaded in 4-bit (`bitsandbytes`, nf4) at runtime.

Turbo defaults (baked in, per the model card: 8 NFEs, CFG-free): `steps=8`,
`guidance_scale=0.0`. Default size: `1024x1024`.

Unlike `upscaler`, the model is loaded **eagerly at server startup** (not
lazily on first request) — `/status` only reports `model_loaded: true` once
the 4-bit text encoder and GGUF transformer are fully warm, since that load
is slow and mixing it into a request's latency would be confusing.

## Safety checker

Every generated image is checked by [Falconsai/nsfw_image_detection](https://huggingface.co/Falconsai/nsfw_image_detection)
(ViT-base/16, Apache-2.0, ~86M params) before being returned or saved --
baked into `generate_bytes()` in `lib/engine.py`, so it applies to every
surface (CLI/HTTP/MCP) with no way to bypass it per-surface. Runs on CPU:
tiny next to the generation pipeline, and never competes with it for VRAM.

A flagged image raises `ContentRefusedError` (`lib/safety.py`), mapped onto
each surface's own convention (there's no single cross-protocol standard):

| Surface | Refusal |
|---|---|
| CLI | exit code `2` (vs. `1` for other failures), message on stderr |
| HTTP | job fails with `error_code: "content_policy_violation"`; `GET .../result` returns `400` with that same code (matches OpenAI's image API convention) |
| MCP | `isError: true` with a descriptive message (MCP has no dedicated error-code system) |

Run your own safety checker instead (upstream, downstream, or by patching
`lib/safety.py`) by setting `SAFETY_CHECKER=disabled`.

## Build

```bash
./scripts/download_zimage_models.sh
./scripts/build_txt2img_model_server.sh
```

## CLI

```bash
docker run --rm --gpus all \
  -v "$(pwd)/txt2img/output:/data" \
  sinanozel/txt2img:zimage-cuda \
  generate --prompt "three cute cats playing" --output /data/out.png
```

## HTTP (async job)

```bash
docker run -d --gpus all -p 8080:8080 sinanozel/txt2img:zimage-cuda

# Submit
curl -X POST http://localhost:8080/v1/generate \
  -H "Content-Type: application/json" \
  -d '{"prompt": "three cute cats playing", "steps": 8}'
# -> {"job_id": "8f14e45f-ceea-4e94-b4c3-8ddd9e2b0e18", "status": "queued", "queue_position": 0}

# Poll
curl http://localhost:8080/v1/generate/8f14e45f-ceea-4e94-b4c3-8ddd9e2b0e18
# -> {"job_id": "...", "status": "completed", "progress": 1.0, "queue_position": null, "error": null}

# Download
curl http://localhost:8080/v1/generate/8f14e45f-ceea-4e94-b4c3-8ddd9e2b0e18/result \
  -o out.png
```

## Job queue

Submissions to `POST /v1/generate` are never rejected for capacity -- they're
queued and run strictly one at a time, in submission order (`lib/jobs.py`:
one worker thread, one pipeline, one GPU). `GET /v1/generate/{job_id}`
reports `queue_position` (`0` = running/next up, `N` = N jobs ahead, `null`
once finished).

The MCP tool doesn't queue -- since it's a synchronous call, sitting behind
someone else's job would just hang the caller. Instead it checks whether a
job is already in flight and, if so, refuses immediately with an error
naming that job's id, directing the caller to `POST /v1/generate` /
`GET /v1/generate/{job_id}` instead of retrying the tool call.

Full OpenAPI docs (generated by `scripts/print_txt2img_openapi.sh`) live under
`txt2img/openapi/`.

## MCP (stdio)

```
generate_image(prompt: str, negative_prompt: str = "", steps: int = 8, guidance_scale: float = 0.0, width: int = 1024, height: int = 1024, seed: int | None = None) -> {image_base64: str, width: int, height: int}
```

## MCP (Streamable HTTP)

Same tool, at `/mcp` on the HTTP server -- no separate container/mode needed.
See `txt2img/tests/mcp_http_client_test.py` for a full working client.

## Tests

Each interface is tested independently, against the real built image:

```bash
./scripts/test_txt2img_cli.sh
./scripts/test_txt2img_http.sh
./scripts/test_txt2img_mcp.sh
./scripts/test_txt2img_safety.sh
```

They use a small size/step count (256x256, 4 steps) to keep test wall-clock
time down -- model load on first request dominates regardless.

`test_txt2img_safety.sh` verifies the refusal wiring above (exit code /
HTTP status / MCP error shape) using `SAFETY_CHECKER=always_refuse`, a
test-only override -- deliberately not by generating or storing actual NSFW
content. It's testing our own mapping, not the classifier's accuracy
(Falconsai's concern, already benchmarked at ~98% on their eval set).
